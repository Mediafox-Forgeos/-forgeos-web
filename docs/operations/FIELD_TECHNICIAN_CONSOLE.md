# Field Technician Console

**Work order:** WO-ARGOS-036 (Field Technician Console)
**Status:** DESIGN. No code, API, migration, or `schema.prisma` change this round — see "Why this stays design-only" at the end of this document for the specific reason this work order's own "if implementation is required" hedge resolves to _not yet_, not a scope judgment made lightly.
**Mission:** the first operational surface field technicians can use themselves — `/my-work` and `/my-work/[id]` — so a technician can answer what to do today, what's most urgent, where to go, what happened before they arrived, what evidence to provide, and what's already done.

## The one fact that has to be resolved before any screen can be designed

Every prior document in this engagement that touched field technicians — [TECHNICIAN_MODEL.md](./TECHNICIAN_MODEL.md) (WO-ARGOS-033), [OPERATIONAL_ACTORS.md](./OPERATIONAL_ACTORS.md) and [DAILY_OPERATION_MAP.md](./DAILY_OPERATION_MAP.md) (WO-ARGOS-034), and [WORK_ORDER_V1_TECHNICAL_NOTES.md](../implementation/WORK_ORDER_V1_TECHNICAL_NOTES.md) (WO-ARGOS-035) — arrived at the same conclusion independently: **a Field Technician has zero product access, by deliberate design.** `WorkOrder.assignedMemberId` points at a real `User`, not a technician-specific identity; `Technician` (as designed in WO-ARGOS-033) was never implemented as a login-capable actor at all. This work order's mission — give technicians their own screen — is not an extension of that design, it's a reversal of it, and reversing a considered decision deserves the same explicit treatment this document is giving it, not a silent assumption.

### The identity question, with a recommendation

Two real paths exist, and this document picks one to recommend rather than leaving the choice unexamined:

- **Option A (recommended): a real `MemberRole.TECHNICIAN`.** Add a seventh value to the existing, real `MemberRole` enum (`OWNER`/`ADMIN`/`OPERATOR`/`SUPPORT`/`ANALYST`/`VIEWER`). A technician gets a real `User` + `Membership`, logs in through the exact same authentication flow every other MOVOS user already uses, and every route this document designs is gated by that role the same way `@Roles()` already gates every other controller in this API. Nothing about login, JWT issuance, or session handling needs to be invented — only a new role value and a new, narrower authorization scope (a `TECHNICIAN` can only see and act on `WorkOrder`s where `assignedMemberId` is their own id; no fleet-wide visibility, no other screen).
- **Option B: a separate, lighter-weight technician auth** (a per-work-order magic link, a PIN, an SMS code) — decoupled entirely from the `User`/`Membership` system. Lower friction for someone who may never need a "real" MOVOS account otherwise, but a second, parallel identity system this codebase has never needed before, with its own security surface (link expiry, replay, revocation) to design and maintain.

**Recommendation: Option A.** It reuses real, already-hardened infrastructure (this repository's entire authentication foundation, `JwtAuthGuard`/`OrgContextGuard`/`RolesGuard`) instead of building a second identity system alongside it, and it's consistent with [OPERATIONAL_ACTORS.md](./OPERATIONAL_ACTORS.md)'s own finding that MOVOS's role vocabulary has repeatedly turned out to already anticipate the real actor MOVOS needed (`SUPPORT`, `ANALYST` — real, shipped roles waiting for their first feature). A `TECHNICIAN` role is the same pattern one more time, not a new one.

**What this recommendation does not do:** implement itself. Adding a `MemberRole` value is a real, if small, migration — and per [OPERATIONAL_ACTORS.md](./OPERATIONAL_ACTORS.md)'s own already-found gap (no `@Roles()` enforcement exists on `ActionController`'s write routes today), getting the authorization boundary right for a role that can see _less_ than every existing role deserves its own careful implementation pass, not a rushed addition alongside three other new screens.

## What this console reuses vs. what's new

The central design insight of this whole document: **the Field Technician Console needs no new data model.** `WorkOrder` and `WorkOrderEvent` (WO-ARGOS-035) already carry everything a technician needs to see — the same rows, the same fields, the same event log an operator already sees on `/work-orders/[id]`. What's new is:

1. **A narrower authorization scope** — a technician sees only `WorkOrder`s where `assignedMemberId` equals their own id, never the full organization's queue.
2. **A different information hierarchy** — single-task focus instead of a fleet-wide list, optimized for someone standing at a station with a phone or tablet, not sitting at a desk triaging many problems at once.
3. **Two new transitions** on the existing state machine — `pause` and a formalized `resolve`-with-checklist — addressed in [WORK_ORDER_CHECKLISTS.md](./WORK_ORDER_CHECKLISTS.md).

## Screen 1 — `/my-work`

**Question answered:** "What do I need to do today, and which is most urgent?"

Four sections, each a real, filterable slice of the same `GET /work-orders` data (scoped to `assignedMemberId = self`, a filter that doesn't exist yet on that endpoint and would need to be added):

| Section         | Real filter                                   | Sort                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Overdue         | `status != RESOLVED/CANCELLED` and past due   | By how overdue — **honest gap:** V1 `WorkOrder` has no `dueAt`/`slaMinutes` ([WORK_ORDER_V1_TECHNICAL_NOTES.md](../implementation/WORK_ORDER_V1_TECHNICAL_NOTES.md)'s own named limitation), so this section has nothing to compute from yet. It should render honestly empty/disabled rather than approximate an SLA that doesn't exist, the same discipline [KYLUM_CONSOLE_WIREFRAMES.md](../product/KYLUM_CONSOLE_WIREFRAMES.md) already applied to "Técnicos en ruta." |
| In progress     | `status = IN_PROGRESS`                        | By priority, then age                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Assigned        | `status = ASSIGNED`                           | By priority, then age                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Completed today | `status = RESOLVED` and `resolvedAt` is today | By `resolvedAt`, most recent first                                                                                                                                                                                                                                                                                                                                                                                                                                         |

Columns per row: priority, station, age, SLA status (honestly disabled per above), current status — matching the mission's literal list.

## Screen 2 — `/my-work/[id]`

**Question answered:** "What exactly is happening with this problem, and what do I do about it?"

| Section          | Source                                                                    | Honest note                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Station summary  | `GET /charging-stations/:id`, same call `/work-orders/[id]` already makes | Fully real, no gap                                                                                                                                                                                                                                                                                                                                                                                              |
| Incident summary | `WorkOrder.description`                                                   | V1 `WorkOrder` has no `incidentId` link back to the originating `Action`/recommendation ([WORK_ORDER_DOMAIN.md](./WORK_ORDER_DOMAIN.md)'s field was dropped from the V1 implementation) — a technician sees the description snapshotted at creation, not the full evidence array an operator sees on the originating recommendation. Real, but narrower than "what happened before I arrived" ideally deserves. |
| Timeline         | `WorkOrderEvent[]`, same data the operator's detail page already renders  | Fully real                                                                                                                                                                                                                                                                                                                                                                                                      |
| Notes            | `WorkOrder.notes` + comment history                                       | Fully real                                                                                                                                                                                                                                                                                                                                                                                                      |
| Event history    | Same as timeline, filtered/framed for a single-task view                  | Fully real                                                                                                                                                                                                                                                                                                                                                                                                      |
| Checklist        | New — see [WORK_ORDER_CHECKLISTS.md](./WORK_ORDER_CHECKLISTS.md)          | Designed, not built                                                                                                                                                                                                                                                                                                                                                                                             |

**Actions:** `start work` (existing `start` transition, unchanged), `add note` (existing `comment` transition, unchanged), `resolve work order` (existing `resolve` transition, now gated by checklist completion — see checklist doc), and **`pause work` — new.** V1's state machine ([WORK_ORDER_V1_TECHNICAL_NOTES.md](../implementation/WORK_ORDER_V1_TECHNICAL_NOTES.md)) deliberately excluded `BLOCKED`/`block` from the full design ([WORK_ORDER_STATES.md](./WORK_ORDER_STATES.md)) as out of scope for a first pass. This work order's own Screen 2 spec asks for it back. This document does not silently reintroduce it — it names the need and defers the actual state-machine change to whatever work order implements this console, so the transition-map change gets the same explicit review every other state-machine change in this engagement has had.

## Screen 3 — "My Day"

**Question answered:** "How is my day going?"

Not a separate route — folded into the top of `/my-work` as a summary strip, since the mission's deliverables list only names two routes (`/my-work`, `/my-work/[id]`) and a third screen with no route of its own reads as a section, not a destination.

- **Completed tasks today** — count of `RESOLVED` work orders with `resolvedAt` today, same query as the "Completed today" section above, just summarized as a number.
- **Active tasks** — count of `ASSIGNED` + `IN_PROGRESS` work orders assigned to this technician right now.
- **Average resolution time** — `AVG(resolvedAt - startedAt)` over this technician's own resolved work orders — real, computable from fields that already exist, the same [LEARNING_METRICS.md](../product/LEARNING_METRICS.md)-style metric shape already established for recommendation types, applied here to a person instead of a detector for the first time.
- **Today's workload** — total work orders touched today (created, started, or resolved), a simple count.

## Why this stays design-only

Three real, unresolved decisions stack up across this document and [WORK_ORDER_CHECKLISTS.md](./WORK_ORDER_CHECKLISTS.md): a new `MemberRole` value (an identity/auth change, the most sensitive category of schema change in this codebase), a new `pause`/`BLOCKED` state-machine transition (a real behavior change to an already-shipped state machine), and a checklist data shape (new structured content inside `WorkOrderEvent.payload`, not a new table, but still a new contract). None of these were designed and reviewed before this work order arrived, unlike WO-ARGOS-035's implementation, which had two full review cycles (WO-ARGOS-033, WO-ARGOS-034) behind it before a single line of code was written. Implementing against undecided identity architecture would mean making that decision unilaterally, live, inside an "implementation" work order — exactly the kind of significant, hard-to-reverse call this engagement has consistently routed through an explicit design-then-build pattern (WO-ARGOS-030 → 031; WO-ARGOS-033/034 → 035) rather than deciding in the same pass it gets built. This document, [TECHNICIAN_WORKFLOW.md](./TECHNICIAN_WORKFLOW.md), and [WORK_ORDER_CHECKLISTS.md](./WORK_ORDER_CHECKLISTS.md) are that design pass.
