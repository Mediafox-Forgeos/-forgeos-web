# CAP-007 — Validation Report

Performed against a compiled `apps/movos-api` instance (`node dist/main.js`), real local PostgreSQL (`movos_dev`), and real HTTP requests (`curl`) — no code path under test was stubbed or mocked. Two organizations ("Tenant Alpha", "Tenant Beta") and one dual-membership user were seeded directly via Prisma (no `POST /organizations` endpoint exists — confirmed in the API audit — organization creation is necessarily out-of-band today), then every subsequent step used the real, running HTTP API exactly as a real client would.

## Setup

- `Tenant Alpha` (org), `Tenant Beta` (org) — created fresh, no relation to the pilot `Kylum Energy` organization.
- One user with two ACTIVE `Membership` rows, `OWNER` role in both orgs — the WO's "same user with multiple memberships" scenario.
- `Sitio Alpha` under Tenant Alpha, `Sitio Beta` under Tenant Beta.
- `ChargingStation` named **"Estación Norte" in both** — the WO's "same station name" scenario.
- One `Evse`/`Connector` per station, **both connectors using externalId `"1"`** — the WO's "same connector number" scenario.

## Cleanup

All seeded rows (2 organizations, 2 sites, 2 stations, 2 evses, 2 connectors, 2 credentials, 1 user, its memberships and refresh sessions) were deleted from `movos_dev` after validation, deepest-first respecting the `RESTRICT` foreign keys documented in CAP-007_ISOLATION_INVARIANTS.md (which is itself why the first delete attempt on the test user failed until its `RefreshSession` rows were removed first — a live, incidental confirmation that `RefreshSession.userId → User` really is `ON DELETE RESTRICT`, not an assumption). Temporary seed/validation scripts were deleted; the server process was stopped after the run completed.

## What this validates vs. what it doesn't

This proves the _existing_ isolation architecture holds under the WO's exact named scenarios, live, against real Postgres and a real running server — it does not constitute a security penetration test (no attempt was made to bypass JWT validation, forge tokens, or exploit anything below the HTTP/ORM layer) and does not cover concurrent/race-condition access to the same resource across tenants (not this work order's concern — see CAP-006A for the project's concurrency-hardening work, which is unrelated to tenant isolation specifically).
