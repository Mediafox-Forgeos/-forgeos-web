# CAP-007 — LocationController Isolation Clarification

**Generated:** 2026-08-02 (WO-ARGOS-013A)
**Status:** Documentation only. No production code, schema, guard, or API was modified to produce this document.
**Trigger:** ARGOS's review of PR #29 flagged `LocationController`'s missing `OrgContextGuard` as an item requiring written justification before merge.
**Companion to:** [CAP-007_API_TENANT_MATRIX.md](./CAP-007_API_TENANT_MATRIX.md) (the original finding), [CAP-007_ISOLATION_INVARIANTS.md](../domain/CAP-007_ISOLATION_INVARIANTS.md)

## Objective 1 — Request flow audit

```
HTTP Request
    │  GET /api/v1/locations/autocomplete?input=...&sessionToken=...
    │  GET /api/v1/locations/place/:placeId?sessionToken=...
    ▼
LocationController  (src/location/location.controller.ts)
    │  @UseGuards(JwtAuthGuard) — class-level, the ONLY guard on this controller
    ▼
JwtAuthGuard  (src/auth/guards/jwt-auth.guard.ts)
    │  A thin wrapper over Passport's 'jwt' strategy — verifies the bearer
    │  token's signature and expiry, and that it decodes to a real,
    │  ACTIVE User. This is authentication only: "is the caller a real,
    │  logged-in MOVOS user?" It resolves no organization, attaches no
    │  membership, and makes no tenant-scoping decision of any kind —
    │  that is exclusively OrgContextGuard's job, and OrgContextGuard is
    │  not present anywhere in this controller's guard chain.
    ▼
LocationController handler
    │  Reads validated DTO fields only: `input`/`sessionToken`/`region`/
    │  `language` (autocomplete) or `placeId`/`sessionToken`/`language`
    │  (place details) — see AutocompleteQueryDto/PlaceQueryDto. Neither
    │  DTO declares an `organizationId`, `siteId`, or any other
    │  MOVOS-owned identifier. There is no tenant-scoped input for a
    │  guard or query filter to ever act on.
    ▼
LocationService  (src/location/location.service.ts)
    │  Pure pass-through: validates `input.length >= 3`, applies default
    │  region/language, and calls GoogleMapsAdapter. No PrismaService
    │  dependency — confirmed by reading the class's constructor
    │  (`constructor(private readonly maps: GoogleMapsAdapter) {}`,
    │  nothing else injected).
    ▼
GoogleMapsAdapter  (src/location/google-maps.adapter.ts)
    │  Constructor dependencies: only `ConfigService` (reads
    │  `MOVOS_GOOGLE_MAPS_SERVER_API_KEY`). Instantiates a
    │  `@googlemaps/google-maps-services-js` `Client` — an HTTP client
    │  for Google's own external API. No PrismaService anywhere in this
    │  file, no import of any MOVOS model type.
    ▼
Google Places API  (external, Google-owned, outside this codebase entirely)
    │  `client.placeAutocomplete({...})` / `client.placeDetails({...})`
    │  — a real outbound HTTPS call to Google's servers.
    ▼
Database query
    │  NONE. There is no step in this entire chain that constructs,
    │  sends, or receives a SQL query, a Prisma call, or any read/write
    │  against MOVOS's own PostgreSQL database. "Database query" is not
    │  a step this request flow has.
```

**Where each concern is (or isn't) handled:**

| Concern                | Where it happens                                                                                                                                                                         | Evidence                                                                                    |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Tenant isolation       | **Nowhere in this flow — not applicable, not missing.**                                                                                                                                  | No tenant-owned row is ever read or written.                                                |
| Permission enforcement | `JwtAuthGuard` only — "is this a valid, logged-in user," nothing more.                                                                                                                   | `@UseGuards(JwtAuthGuard)`, no `@Roles(...)`, no `RolesGuard`.                              |
| Organization scoping   | **Nowhere.**                                                                                                                                                                             | No `OrgContextGuard`, no `organizationId` parameter anywhere in the DTOs or the call chain. |
| Data filtering         | **Nowhere — because there is no MOVOS data to filter.** Google's own API decides what results to return, filtered only by `input`/`region`/`language`, none of which are MOVOS concepts. | `GoogleMapsAdapter` methods take no MOVOS identifier as a parameter.                        |

## Objective 2 — Query analysis

**Query source:** two Google Places API calls — `client.placeAutocomplete(...)` and `client.placeDetails(...)`, both defined in `@googlemaps/google-maps-services-js`, both executing an outbound HTTPS request to `maps.googleapis.com` (or the library's configured endpoint). **Zero Prisma queries.** Confirmed by grep: neither `location.controller.ts`, `location.service.ts`, nor `google-maps.adapter.ts` imports `PrismaService`, `@prisma/client`, or any generated Prisma type.

**Organization filters:** none exist to check — there is no query against MOVOS data for a filter to be present or absent from.

**Joins:** none — no ORM/SQL layer is invoked at all in this request path.

**Ownership constraints:** none apply — Google Places results (an address suggestion, a resolved lat/lng) are not MOVOS-owned rows and have no `organizationId` to constrain.

### Can Organization A retrieve Organization B's data via this controller?

# **NO**

**Justification:** "Organization B's data" refers to rows in MOVOS's own database scoped to Organization B (its Sites, ChargingStations, Sessions, Credentials, etc.). `LocationController` never queries MOVOS's database in any code path — not for Organization A, not for Organization B, not for any organization. It is architecturally incapable of returning "someone else's data" because it returns no MOVOS-owned data to _anyone_, including the caller's own organization. The only data it returns is Google's own public geocoding/places information (a street address, a formatted address string, a latitude/longitude) — identical, public information Google would return to any caller, from any company, MOVOS-related or not, who queried the same `input`/`placeId`. There is no "Organization B's version" of a Google Places result to leak, because Google Places results are not organization-scoped data in the first place — they describe real-world addresses, not MOVOS tenant records.

## Objective 3 — Runtime proof

**Not previously covered by CAP-007_VALIDATION.md** — that report's scenarios were scoped to the tenant-owned endpoints (Sites, ChargingStations, Connectors, Credentials); `LocationController` was evaluated by static code analysis only in CAP-007, not runtime-tested. This work order's explicit request for runtime proof was therefore executed fresh, now, rather than retroactively described from a test that didn't target this controller. Same discipline as every other runtime validation in this project: real booted server, real local PostgreSQL (`movos_dev`), real HTTP requests.

**Setup:** two fresh organizations ("Tenant Gamma", "Tenant Delta") and one user with an ACTIVE `Membership` in both, seeded directly via Prisma (mirroring CAP-007's original setup) — then torn down after the run.

**One residual item worth naming, distinct from tenant isolation:** Google Maps API usage/cost is not currently attributed per-organization (since no organization context is used at all here) — if per-tenant API-cost accounting or per-tenant rate limiting ever becomes a business requirement, that would need its own design (e.g. a lightweight org-aware request counter, independent of `OrgContextGuard`'s membership-authorization purpose). This is a cost/fairness concern, not a data-isolation one, and is explicitly out of this work order's scope.

## Objective 5 — Final verdict

# **A. LocationController is safe as implemented.**

**Justification, weighed directly against option B ("safe but misleading, needs future refactoring"):** Option B would apply if the _absence_ of `OrgContextGuard` created a plausible expectation of tenant-scoped behavior that the implementation quietly fails to deliver — e.g., if the DTOs accepted an `organizationId` that was silently ignored, or if the route lived under a URL pattern implying tenant scope (`/organizations/:id/locations/...`), or if any MOVOS entity were ever read through this path. None of those are true here: the routes are `/locations/autocomplete` and `/locations/place/:placeId` — no tenant segment in the path, no tenant field in either DTO, and (per CAP-007_API_TENANT_MATRIX.md's original finding, reaffirmed and now runtime-proven here) every _other_ controller in this codebase that does touch tenant data is guarded consistently. `LocationController`'s guard stack isn't an inconsistency that happens to be harmless — it's the _correct_ guard stack for a controller that authenticates the caller (a real requirement — this isn't a public, unauthenticated proxy) but has no organization-scoped resource to authorize against. Calling this "misleading" would require a reasonable reader to expect tenant scoping from a stateless external-API proxy with no tenant-shaped inputs, which this audit's evidence doesn't support.

**Why not C:** every objective above — the flow trace, the query analysis, the live runtime proof across four organization-context permutations (including a bogus-membership case that would return `403` on every other controller and instead returns identical `200` here because there is no membership check to fail), and the threat model — converges on the same finding: there is no MOVOS-owned, tenant-scoped data anywhere in this request's reach. "Vulnerable" would require a plausible path from an authenticated caller to another organization's data; no such path was found, constructed, or is constructible without this controller first being changed to accept and use a tenant-scoped parameter it currently has no reason to accept.

**Recommendation carried forward from CAP-007 (unchanged):** if `LocationController` ever gains a route that reads or writes MOVOS tenant data, add `OrgContextGuard` to that new route at that time — this verdict is scoped to the two routes as they exist today, not a permanent exemption for the controller regardless of what's added to it later.
