# CAP-007 — API Tenant Matrix

**Companion to:** [CAP-007_TENANT_MODEL.md](../domain/CAP-007_TENANT_MODEL.md), [CAP-007_ISOLATION_INVARIANTS.md](../domain/CAP-007_ISOLATION_INVARIANTS.md)

## Headline finding

**No route was found where an authenticated user could read or mutate a row belonging to an organization they do not hold an ACTIVE `Membership` in.** The isolation pattern is defense-in-depth and applied consistently: `OrgContextGuard` authenticates the caller and re-validates their membership server-side (never trusting a client-supplied org id directly — see mechanism below), and every service method independently re-scopes its own query by `organizationId` (or a chain of `findFirst`/ownership checks that terminates in `organizationId`) before both reads and writes. A client cannot smuggle a spoofed `organizationId` into a request body either — `main.ts`'s global `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })` strips/rejects unrecognized fields.

## Guard mechanism (verified by reading the source, not assumed)

- **`OrgContextGuard`**: resolves the "active organization" from the `X-Organization-Id` header, falling back to the `orgId` claim in the JWT. **Always re-validates server-side** — looks up `Membership` by the exact `(userId, organizationId)` pair and requires `status === 'ACTIVE'`; throws `ForbiddenException` otherwise. The client-supplied value only selects _which_ membership to check — it is never trusted as authorization on its own. Attaches the resolved `Membership` (containing `organizationId` and `role`) to the request for downstream use via `@OrgContext()`.
- **`RolesGuard`**: reads `@Roles(...)` metadata; if none declared, allows any authenticated, org-context-resolved caller through. If declared, requires the resolved `membership.role` to be in the allowed set.
- **Neither guard filters a query by itself** — `OrgContextGuard` only gates _access_, establishing which organization is active; every controller's service layer is independently responsible for using `membership.organizationId` in its own Prisma `where` clause. This was verified per-route below, not assumed from the guard's presence.
- **`@OrgContext()`** fails fast (throws a hard `Error`, not a silent `undefined`) if used without `OrgContextGuard` wired first — a structural guard against a controller author forgetting the guard.

## Evaluated inconsistency: `LocationController`

`GET /locations/autocomplete` and `GET /locations/place/:placeId` carry `JwtAuthGuard` only, not the `OrgContextGuard`/`RolesGuard` pair every other authenticated controller uses. **This is not a tenant-isolation gap** — these routes are stateless proxies to the Google Places API, read no tenant-owned row, write no tenant-owned row, and take no `organizationId` parameter; there is no organization-scoped data for a missing guard to fail to protect. It is flagged here as a structural inconsistency worth being deliberate about, not fixed by this work order: adding `OrgContextGuard` now would require every caller of `/locations/*` (the Site-creation and Site-edit flows in `apps/movos-web`) to always have an active-organization header present, a behavior change to a currently-working feature with no isolation benefit to justify the risk. **Recommendation, not implemented:** if `LocationController` ever gains a route that reads or writes tenant-scoped data, add `OrgContextGuard` to that new route (or promote it to the class level) at that time — don't carry this inconsistency forward by assuming the next route added here is safe by default.

## Read-route role permissiveness — evaluated, confirmed intentional

Every `GET` route across every controller above is `roles-gated: no (any role)` — `VIEWER` can read exactly the same data `OWNER` can within their own organization. This is consistent everywhere (no controller is an exception) and matches the stated rule "VIEWER cannot modify data" precisely — the constraint the codebase actually enforces is on _mutation_, not on _read breadth within one's own tenant_. Confirmed as the intended design, not an oversight: every `POST`/`PATCH` route above does carry an explicit `@Roles(...)` restriction.
