## What "requiere nuevo dominio" costs beyond the migration itself

Three rows above (`ATTENTION_QUEUE`, incident table, maintenance ticket table) share a dependency the query column doesn't fully capture: every one of them needs `AlertDetectionService` (Sprint 2's event-wiring work, [CAPX_COMPONENT_MAP.md](./CAPX_COMPONENT_MAP.md)) to actually populate rows before any query above returns something meaningful. A correct migration with zero rows in it demonstrates nothing — this is why [CAPX_SPRINT_PLAN.md](./CAPX_SPRINT_PLAN.md) treats Sprint 2 as one unit (migration + detection wiring + UI) rather than three separable pieces that could be sequenced independently.

## Fields this plan needs that already exist, named precisely

To keep every query above grounded rather than aspirational, the exact existing fields each one reads:

- `ChargingStation.connectivityStatus`, `Evse.status`, `Connector.status` — all real, all populated (CAP-002/CAP-005).
- `ChargingSession.status`, `.energyWh`, `.startedAt`, `.endedAt`, `.terminationReason`, `.updatedAt` — all real, all populated (CAP-004).
- `Site.latitude`, `.longitude` — real, production-grade (Location capability).
- `Organization`/`Site` scoping on every query above — mandatory, following the same `organizationId`-first-filter discipline every existing query in this codebase already applies via `OrgContextGuard`; no query in this document is written without it.

Nothing in this table invents a field this plan hasn't already confirmed exists in `schema.prisma`.
