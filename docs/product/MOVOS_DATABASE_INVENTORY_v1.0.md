## Maturity and gaps

- IDs are `cuid()` everywhere — no sequential integers exposed. Sound baseline hygiene.
- No indexes exist beyond primary keys and the unique constraints above. `AuditEvent` has none on `organizationId` or `occurredAt`, despite being the one table with no natural growth ceiling — this will matter once audit queries by date range become real usage, not before.
- `Site.locationValidatedAt` is defined in the schema but never written to by any service code (`sites.service.ts`) — a field that exists with no code path that populates it.
- Soft-delete precedent exists only via `Site.status = ARCHIVED`; `ChargingStation`/`Evse`/`Connector` follow the same convention (status-based deactivation, no hard delete).
- `Evse` and `Connector` deliberately store no `organizationId` or `siteId` — ownership resolves through the parent relation chain (`evse.chargingStation.site.organizationId`) in a single Prisma query at every service call, never a denormalized column.
- Still zero models for `Tariff` or `Alert`. CAP-002 explicitly implements CRUD for `ChargingStation`/`Evse`/`Connector` only. CAP-003 (WO-ARGOS-007) added device identity/authentication fields and an append-only `OcppProtocolEvent` log. CAP-004 (WO-ARGOS-009) added `ChargingSession`/`AuthorizationCredential`/`AuthorizationAttempt`/`MeterValue` — but still no `Driver`/`Vehicle`/`Fleet`, tariff, reservation, or payment models, per this WO's explicit instruction not to create speculative tables for future capabilities merely to reserve names.
- `OcppProtocolEvent` is append-only and unbounded by any code-enforced retention today — the retention policy is documented (see the model's schema comment and the [OCPP Engine Guide](../engineering/OCPP_ENGINE_GUIDE.md)) but not yet automated; this is a known, tracked gap, not an oversight (Decision 5's refinement: "unlimited telemetry retention is forbidden without an explicit policy").
- `ChargingSession` is the first table in this schema to store `organizationId`/`siteId`/`chargingStationId`/`evseId`/`connectorId` directly rather than deriving them through the parent chain — a deliberate, documented exception (CAP-004_CHARGING_SESSIONS_FOUNDATION.md §2), not an inconsistency with the `Evse`/`Connector` pattern above.
- `ChargingSession`/`MeterValue` have `CHECK` constraints enforcing non-negative energy/meter values at the database level, in addition to application-layer checks in `SessionLifecycleService` — the first models in this schema to use a `CHECK` constraint rather than relying on application code alone.

## What the frontend already assumes, that the schema doesn't have yet

`apps/movos-web/src/types/{station,charger,connector,session,tariff,alert}.ts` define a complete TypeScript shape for these entities. CAP-002 implements the backend for `station`/`charger`/`connector` only (as `ChargingStation`/`Evse`/`Connector` — not a 1:1 rename; see [CAP-002 Charging Terminology Mapping](../domain/CAP-002_CHARGING_TERMINOLOGY_MAPPING.md)), and does not yet update the frontend to consume it. CAP-004 (WO-ARGOS-009) now implements a real backend for `session` too (as `ChargingSession` — not a 1:1 rename either), but the frontend has not been migrated to consume it; `apps/movos-web`'s mock session type/routes remain unchanged. `tariff` and `alert` remain frontend-only design work with no backend counterpart. See [MVP Gap Analysis](./MOVOS_MVP_GAP_ANALYSIS_v1.0.md).
