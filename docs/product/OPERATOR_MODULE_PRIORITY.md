# Operator Module Priority

**Work order:** WO-ARGOS-018 (CAP-X Discovery — Operator Control Center)
**Status:** PRODUCT DISCOVERY. Classification only — no module below is authorized for implementation by this document. Priority is evaluated against the operator (not driver) as customer, per [OPERATOR_DAILY_WORKFLOW.md](./OPERATOR_DAILY_WORKFLOW.md).
**Method:** each module is scored against three questions — does an operator need this to know their business is functioning _today_, does the underlying data already exist in MOVOS, and does withholding it actively erode trust in the product. P0 fails none of these; P2 fails at least the first.

## Reading this table against what's already built

Three modules — **charger monitoring**, **alerts**, and **real-time map** — are P0 specifically because they share a property none of the others do: the underlying data already exists in a schema that has been through multiple ARGOS-reviewed hardening cycles (CAP-002 through CAP-005), and the only missing piece is aggregation and presentation, not new domain modeling, new device integration, or new business logic. This is a materially different, and cheaper, kind of work than what CAP-009 required (new entities, new invariants, new migrations) or what Billing/Invoices (CAP-010) will require (new financial logic, new external integrations).

**Occupancy** and **Analytics** are P1 for the same reason — real underlying data, presentation-layer work only — but are sequenced behind the P0 set because they answer secondary questions ("how busy," "what's the trend") rather than the primary one ("is it working right now").

**Tariffs and Billing/Invoices** are P1 despite being commercially essential, because they are not _daily_ operational screens in the way charger status and alerts are — see [OPERATOR_DAILY_WORKFLOW.md](./OPERATOR_DAILY_WORKFLOW.md), which never names "check today's invoices" as a first-screen action for any of the five operator shapes. This is the load-bearing finding for [OPERATOR_STRATEGY_RECOMMENDATION.md](./OPERATOR_STRATEGY_RECOMMENDATION.md).

**Maintenance, Customer Support, and Reservations** are lowest priority not because they lack value, but because each depends on a P0/P1 module existing first (Maintenance needs Alerts; Customer Support needs a queryable incident/session history view; Reservations has no evidence of operator-side urgency at all in this discovery).
