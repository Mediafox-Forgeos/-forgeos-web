# CAP-X — MVP Data Matrix

**Work order:** WO-ARGOS-020 (Operator Control Center MVP Definition)
**Status:** PRODUCT DISCOVERY / PLANNING. No code, API, migration, or `schema.prisma` change. This document classifies data, it does not build anything.
**Question posed (Objective 3):** "¿Qué datos pueden mostrarse hoy con CAP-009?" — what can MOVOS show an operator today, as of the current codebase state (CAP-002 through CAP-009, all merged to `main`), and what would each additional data point require?
**Builds on:** [CAP-X_OPERATOR_DOMAIN.md](../domain/CAP-X_OPERATOR_DOMAIN.md), [CAP-X_STATION_HEALTH.md](../domain/CAP-X_STATION_HEALTH.md), [CAP-X_WIDGETS.md](../domain/CAP-X_WIDGETS.md) (WO-ARGOS-019), and [OPERATOR_KPIS.md](./OPERATOR_KPIS.md) (WO-ARGOS-018).

## Classification method

Three buckets, deliberately distinct from each other in a way that matters for a 30-day plan:

- **Disponible hoy (available today):** the exact data point is already returned by an existing, real API endpoint, on an existing model, with zero new code. If a developer needed this tomorrow morning, they'd call an endpoint that already exists.
- **Requiere backend (requires backend work):** the underlying data already exists in real, populated tables (`ChargingStation`/`Evse`/`Connector`/`ChargingSession`/`BillingAccount`, all real schema), but no aggregation, rollup, or new endpoint exposes it in the shape an operator dashboard needs. No `schema.prisma` change — this is service/controller code only.
- **Requiere nuevo dominio (requires a new domain):** no table exists to hold this data at all. Producing it requires the new entities specified in [CAP-X_OPERATOR_DOMAIN.md](../domain/CAP-X_OPERATOR_DOMAIN.md) (`Alert`, `Incident`, `MaintenanceTicket`, `OccupancySnapshot`) — meaning a migration, which this work order does not authorize, but a future implementation work order would need to.

This distinction is the entire point of this document: "requiere backend" is roughly a day-to-week of work per data point with no risk of schema churn; "requiere nuevo dominio" cannot happen at all without a migration landing first, no matter how much backend effort is applied.

## The Revenue exception

Revenue does not fit cleanly into any of the three buckets, and forcing it into one would misrepresent the actual blocker. `TariffSnapshot` is real schema (CAP-009) — this is not a "requiere nuevo dominio" situation for the Operator Control Center's own domain. But nothing in MOVOS today populates a `TariffSnapshot`: no `Tariff` (rate-setting) model exists, no pricing service exists, so every `ChargingSession` today has zero attached `TariffSnapshot` rows. Revenue is not "requiere backend" either — no amount of Operator Control Center backend work produces a price that was never set. This is a dependency on a _different, not-yet-built domain_ (Tariffs, Architecture Backlog #24), consistent with the finding already made in [OPERATOR_KPIS.md](./OPERATOR_KPIS.md) KPI 3 and [OPERATOR_STRATEGY_RECOMMENDATION.md](./OPERATOR_STRATEGY_RECOMMENDATION.md). It is excluded from this MVP's scope entirely — see [CAPX_MVP_WIDGETS.md](./CAPX_MVP_WIDGETS.md).

## What this means for a 30-day window

Reading straight down the matrix: **12 of the 21 classified data points need zero schema change** (9 disponible hoy + a further set squarely in "requiere backend," including the two highest-leverage rows in the whole table — `StationHealth` and the site-level map rollup, both derivable from data that already exists). Only **5 data points require a new migration** (`Alert`, `Attention queue`, `Incidents`, `Maintenance tickets`, `Fault recurrence` — the last two of which additionally require history `Alert`/`Incident` don't need to exist yet for the _first four_ to ship), plus the occupancy-trend row. Revenue is excluded from the 30-day window entirely, on grounds independent of effort.

This shape — most of the value reachable with zero schema risk, a small, well-scoped island requiring one deliberate migration — is what makes a 30-day window plausible at all, and it directly informs the widget/table/action selection in [CAPX_MVP_WIDGETS.md](./CAPX_MVP_WIDGETS.md).
