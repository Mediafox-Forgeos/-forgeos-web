# Pilot Measurement Plan

**Work order:** WO-ARGOS-039
**Method:** every metric below was checked against what the real schema, API, and UI actually expose today — not what would be convenient to have. No analytics, aggregation endpoint, or dashboard was built to produce this plan.

**Classification key:** `AVAILABLE_NOW` (a real number, visible today, with no extra work — usually a count on an existing screen) · `DERIVABLE_NOW` (the real underlying data exists and is queryable/computable, but nothing currently aggregates or displays it as a single stat) · `REQUIRES_NEW_CAPABILITY` (the concept isn't captured by the current data model at all).

## What this means for the pilot's review checkpoint

The five headline numbers a supervisor can pull with zero extra work at the review checkpoint (`OPERATIONAL_PILOT_V1.md`'s "when"), directly off `/work-orders`:

1. `WorkOrder`s created (AVAILABLE_NOW)
2. `WorkOrder`s resolved (AVAILABLE_NOW)
3. Source mix — how many were manual vs. recommendation-triggered vs. automatic (DERIVABLE_NOW, a few minutes of reading the list)
4. Rough cycle time per resolved item — `assignedAt` → `startedAt` → `resolvedAt`, already visible per-`WorkOrder` on its own detail page (DERIVABLE_NOW, same effort as #3)
5. Whether any duplicate ever appeared for the same station during the observation window (DERIVABLE_NOW, the exact check this engagement already performed live during WO-ARGOS-038's validation)

No dashboard, report, or analytics capability needs to be built to produce a credible review at this pilot's scale — a supervisor spending 20–30 minutes with the real `/work-orders` list and the database can answer all five.
