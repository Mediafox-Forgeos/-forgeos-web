# Pilot Dependency Audit

**Work order:** WO-ARGOS-039
**Method:** every item below was checked against real, live evidence where possible — the actual production URLs were queried directly (`curl`, 2026-08-15) rather than assumed from documentation. Where evidence stops at documentation (env var names, deployment process), that's stated explicitly.

**Classification key:** `READY` · `CONFIGURATION_REQUIRED` (the capability/infrastructure exists but needs a real action before pilot day) · `MANUAL_PROCESS_ACCEPTABLE` (no product path exists, but a human doing it once, out of band, is a reasonable trade-off for a pilot this size) · `BLOCKER`.

## The single most important finding in this document

**The live production deployment is real, but drastically out of date.** `movos-api-production.up.railway.app` and `movos-web.vercel.app` are both online right now — confirmed by direct request, not assumed. But `GET /api/v1/work-orders` and `GET /api/v1/my-work` both return `404` (route does not exist), and so do `/actions`, `/recommendations`, and `/charging-stations/:id` — while `/sites` correctly returns `401` (route exists, rejects unauthenticated). This is not a permissions difference; it's the signature of a deployment that predates CAP-002 entirely, let alone the operational loop this pilot is built around. **Nothing in this pilot can run against the current production deployment until it is redeployed from current `main`.**

There is no CI/CD deploy pipeline (`.github/workflows/ci.yml` runs lint/typecheck/test only, no deploy step) — redeployment is a manual `railway deployment up` (API) and `vercel --prod` (web), per this project's own established, undocumented-elsewhere-but-real process.

## What "CONFIGURATION_REQUIRED" adds up to, concretely

Before pilot day, one technical person needs to:

1. Deploy current `main` to the real Railway (`movos-api`) and Vercel (`movos-web`) projects.
2. Run `prisma migrate deploy` against the real production database.
3. Confirm the existing environment variables are current and correct (or set new ones for an isolated pilot environment, if ARGOS prefers not to reuse the existing "Kylum Energy" seeded org for a real pilot — a decision for `PILOT_GO_NO_GO.md`, not assumed here).
4. Complete the onboarding steps in `PILOT_ONBOARDING_REQUIREMENTS.md` against that now-current deployment.

None of this is a code change. All of it is real, bounded, one-time operational work.
