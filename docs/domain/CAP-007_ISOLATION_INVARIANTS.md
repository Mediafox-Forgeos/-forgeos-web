# CAP-007 — Isolation Invariants

**Generated:** 2026-08-02 (WO-ARGOS-013)
**Method:** each invariant checked against the actual schema/migrations/guards/services, not merely stated. Where an invariant was already true before this work order, that is said explicitly, distinguished from anything CAP-007 newly enforces.
**Companion to:** [CAP-007_TENANT_MODEL.md](./CAP-007_TENANT_MODEL.md), [CAP-007_API_TENANT_MATRIX.md](../reviews/CAP-007_API_TENANT_MATRIX.md)

Every invariant below is phrased against `Organization` — the entity WO-ARGOS-013's "Tenant" proposal maps onto (see CAP-007_TENANT_MODEL.md §0).

## Invariant 1 — No tenant can access another tenant's data

**Status: already true, verified exhaustively, not newly added by CAP-007.**

Verified by direct code audit of every `*.controller.ts` route in the API (see CAP-007_API_TENANT_MATRIX.md for the full route-by-route evidence): `OrgContextGuard` re-validates an ACTIVE `Membership` server-side for every request (never trusting a client-supplied organization id alone), and every service method independently re-scopes its own Prisma query by `organizationId` — either directly (denormalized columns) or via a `findFirst`/ownership-chain check that terminates in `organizationId` before any read or write proceeds. No route was found where an authenticated member of one organization could read or mutate a row belonging to another. The one structural inconsistency found (`LocationController` missing `OrgContextGuard`) does not violate this invariant — that controller touches no tenant-owned row.

## Invariant 2 — Sessions inherit tenant ownership

**Status: already true at the database level, not application-level-only.**

`ChargingSession.organizationId` is a required, non-nullable column (not derived at read time through the `Site`/`ChargingStation` chain the way `Evse`/`Connector` are) — a deliberate CAP-004 denormalization. The foreign key is `ON DELETE RESTRICT`: Postgres itself refuses to delete an `Organization` row while any `ChargingSession` still references it, and refuses to insert a `ChargingSession` whose `organizationId` doesn't reference a real `Organization` row. This is stronger than "the application remembers to set it" — the database enforces the row cannot exist without an owning tenant.

## Invariant 3 — Credentials inherit tenant ownership

**Status: already true, and additionally already tenant-scoped for uniqueness, not just ownership.**

`AuthorizationCredential.organizationId` is required, `ON DELETE RESTRICT`, same guarantee as Invariant 2. Additionally — and this directly answers the WO's runtime-validation scenario "two tenants, same RFID" — the uniqueness constraint on `externalIdentifier` (the physical RFID UID or equivalent) is `@@unique([organizationId, externalIdentifier])`, **scoped per-organization, not global**. Two different organizations issuing a card that happens to produce the same raw UID is not just permitted, it was designed for from CAP-004 onward (see the schema comment: "two different organizations may each issue a card that happens to produce the same raw UID on a specific reader/vendor combination"). This is proven live in CAP-007_VALIDATION.md, not just read from the schema comment.

## Invariant 4 — Invoices inherit tenant ownership

**Status: no `Invoice` model exists. This invariant is a forward design constraint on that future work, not a property being verified today.**

Stated explicitly so a future Invoice/Billing capability has a documented starting constraint rather than re-deriving tenant-ownership design from scratch: an `Invoice` model must (a) carry `organizationId` directly (denormalized, matching the `ChargingSession`/`AuthorizationCredential` precedent — an invoice is exactly the kind of row expected to have session-level query volume), (b) use `ON DELETE RESTRICT` on that foreign key, and (c) never be derivable _only_ through a join to `ChargingSession` (a session's own `organizationId` should be consistent with, but not the sole enforcement mechanism for, its invoice's tenant ownership — two independent, agreeing sources of truth, not one). This is guidance for whoever builds Billing, not a schema change made now — inventing an `Invoice` table today would be the exact kind of speculative building this engagement's discipline avoids, and CAP-007 does not do it.

## Invariant 5 — Users only see authorized tenants

**Status: already true, verified.**

`GET /organizations` (`OrganizationsService.listForUser`) filters `Membership.findMany({ where: { userId, status: 'ACTIVE' } })` — a user's own id, not a client-suppliable filter. There is no endpoint anywhere in the API that lists all organizations globally to a non-platform-staff caller (no such endpoint exists at all, in fact — see CAP-007_TENANT_MODEL.md §3.2's `SUPER_ADMIN` design for the only role this invariant is an intentional exception for, and note that role is evaluated, not implemented, so today this invariant has **zero** exceptions in the running system).

## Database requirements — FK, cascade, and constraint audit

Every relation in the schema, verified directly against the generated migration SQL (`ON DELETE` clauses are Prisma's implicit default when no explicit `onDelete` is set — verified this actually produces the intended behavior, not assumed):

| Relation                                                                         | ON DELETE             | Justification                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Membership.userId → User`                                                       | `RESTRICT`            | A `User` row cannot be deleted while they still hold any organization membership — forces an explicit membership-removal step first, preventing an orphaned audit/history trail under a since-deleted user id.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `Membership.organizationId → Organization`                                       | `RESTRICT`            | An `Organization` cannot be deleted while it still has members — the same protection from the tenant's side.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `Site.organizationId → Organization`                                             | `RESTRICT`            | Cannot delete a tenant while it still owns Sites — the first link in the "sessions never exist outside a tenant" chain (Invariant 2 depends on this transitively for every model that derives ownership through `Site`, not just the ones that denormalize it).                                                                                                                                                                                                                                                                                                                                                                                          |
| `Site.createdByUserId → User`                                                    | `RESTRICT`            | Preserves "who created this Site" — cannot delete a user while their historical creation record would be orphaned.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `ChargingStation.siteId → Site`                                                  | `RESTRICT`            | Cannot delete a Site while it still owns stations.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `Evse.chargingStationId → ChargingStation`                                       | `RESTRICT`            | Same pattern one level down.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `Connector.evseId → Evse`                                                        | `RESTRICT`            | Same pattern, the final link — by the time you reach `Connector`, four `RESTRICT`s stand between it and an accidental `Organization` deletion.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `ChargingSession.organizationId/siteId/chargingStationId/evseId/connectorId → *` | `RESTRICT` (all five) | Every denormalized ownership field is independently protected — a session can never be left referencing a deleted parent at any level of the hierarchy, not just at the `Organization` level.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `ChargingSession.authorizationCredentialId → AuthorizationCredential`            | `RESTRICT`            | A credential that authorized a real session can never be hard-deleted — this is what makes "a session's authorization history is permanent" true at the database level, not just a service-layer promise (verified in WO-ARGOS-009A's independent validation of this exact constraint).                                                                                                                                                                                                                                                                                                                                                                  |
| `AuthorizationCredential.organizationId → Organization`                          | `RESTRICT`            | Same tenant-deletion protection as Invariant 3.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `AuthorizationAttempt.organizationId/chargingStationId → *`                      | `RESTRICT`            | The attempt log's required fields are protected the same way.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `AuthorizationAttempt.evseId/connectorId/authorizationCredentialId → *`          | `SET NULL`            | **Deliberately different** — these are optional/nullable on the model already (an attempt might occur before EVSE/connector resolution, or reference a credential that's later legitimately hard-deleted in some future cleanup). `SET NULL` preserves the attempt row itself (the audit-relevant fact "an attempt happened, with this result, at this time" survives) while letting the specific sub-reference go — the opposite tradeoff from `ChargingSession.authorizationCredentialId`, correctly, because `AuthorizationAttempt` is a append-only log entry, not a required, defining reference the way a session's own authorizing credential is. |
| `MeterValue.sessionId → ChargingSession`                                         | `RESTRICT`            | Telemetry cannot outlive its session — but note DEC-016 already establishes a session's energy/meter fields never _depend_ on `MeterValue` rows existing, so this is about referential integrity, not resurrecting the telemetry-independence question.                                                                                                                                                                                                                                                                                                                                                                                                  |
| `AuditEvent.organizationId → Organization`                                       | `SET NULL`            | **Deliberately different from every ownership-chain FK above.** An audit event is a historical record of something that happened — it should outlive the organization it was about (e.g. a record that an organization was archived/deleted is itself worth keeping), and some audit-worthy events (a failed login attempt before any organization is selected) never had an organization to begin with. `SET NULL` here is the correct choice specifically because `AuditEvent` is history, not live ownership data — contrast with `RESTRICT` everywhere ownership is live and structural.                                                             |
| `AuditEvent.actorUserId → User`                                                  | `SET NULL`            | Same reasoning — the audit record survives a user's deletion; only the specific actor-attribution link is cleared.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `OcppProtocolEvent.chargingStationId → ChargingStation`                          | `SET NULL`            | Same historical-record reasoning as `AuditEvent` — a raw protocol frame that arrived before identity resolution, or that references a since-deleted station, still has diagnostic value; it should not vanish or block station deletion.                                                                                                                                                                                                                                                                                                                                                                                                                 |

**Pattern, stated once, that explains every row above:** `RESTRICT` wherever a foreign key represents _live, structural ownership_ (an organization owning its sites, a session belonging to its station, a credential belonging to its tenant) — deletion is blocked rather than silently cascading or orphaning, forcing every ownership change to be an explicit, deliberate, auditable act. `SET NULL` wherever the foreign key is a _historical/diagnostic reference_ on an append-only or audit-style row (`AuditEvent`, `OcppProtocolEvent`, the optional sub-references on `AuthorizationAttempt`) — the record itself must survive its subject's deletion; only the dangling pointer is cleared. **No relation anywhere in the schema uses `CASCADE`** — a deliberate absence: cascading deletes would let deleting one row silently delete an entire subtree (e.g. deleting a `Site` silently deleting every `ChargingStation`/`Evse`/`Connector`/`ChargingSession` beneath it), which is exactly the kind of irreversible, hard-to-audit action this schema's `RESTRICT`-first posture is designed to prevent. This is all existing, shipped behavior — CAP-007 verifies and documents it, and changes none of it.
