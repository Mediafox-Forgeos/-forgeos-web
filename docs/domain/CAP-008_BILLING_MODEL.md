# CAP-008 — Billing Foundation: Domain Model

**Generated:** 2026-08-03 (WO-ARGOS-016)
**Status:** DOCUMENTATION ONLY. No `Invoice`, `Payment`, `Tax`, `Discount`, `Tariff`, or `TariffSnapshot` model is created by this document. No Stripe or accounting integration is designed. `OCPP` and `ChargingSession` are not modified. No UI is built. This document defines the billing **domain** — what money means in MOVOS and where it attaches to the schema that already exists — not an implementation.
**Builds on:** [CAP-004 — Charging Sessions & Authorization Foundation](./CAP-004_CHARGING_SESSIONS_FOUNDATION.md) (authoritative for `ChargingSession`/`AuthorizationCredential` as they are actually shipped), [DEC-018 — Billing Ownership Boundary Analysis](./DEC-018_BILLING_BOUNDARY_ANALYSIS.md) (already recommends a `ChargingSession → TariffSnapshot → Invoice` shape and explicitly leaves open the question this document's Objective 2 addresses), [MOVOS ChargingSession Architecture v0.1](./MOVOS_CHARGING_SESSION_ARCHITECTURE_v0.1.md) (superseded by CAP-004 where they differ; cited here only for still-current conceptual material).
**Grounding discipline:** every claim about current behavior below is verified against the shipped Prisma schema (`apps/movos-api/prisma/schema.prisma`) and service code as of `main` @ `57a36d5`, not assumed or carried over from older documents without re-checking.

---

## Mission

Answer six questions about how money flows through MOVOS, without building any of it:

1. What is billable?
2. When does billing begin?
3. When is pricing frozen?
4. Can pricing change mid-session?
5. Who owns the debt?
6. What must be persisted forever?

The short answers, expanded below: **(1)** the metered energy delivered during a `ChargingSession` — not any party, not any piece of hardware. **(2)** at `StartTransaction`/session creation, the same instant `ChargingSession.startedAt` is set — never earlier (there is no session to bill before one exists) and never later by design (see Objective 2). **(3)/(4)** genuinely open — this is Objective 2's evaluation and Objective 7's decision, not answered here. **(5)** structurally unresolved by the current schema — see Objective 1's headline finding. **(6)** the `ChargingSession` row and whatever pricing-snapshot mechanism Objective 7 selects — both already protected from deletion today by the schema's existing (unintentional but real) referential-integrity defaults, detailed in Objective 3.

## Objective 1 — Billable entities

### The question this objective actually resolves

The work order asks which entity "generates revenue," "receives charges," and "owns the invoice" — three questions that sound like they're about the same thing but are not. Evaluated against the six named candidates, they resolve to **three different entities**, and one of the three has no schema representation at all today. That gap, not a tidy three-way mapping, is this objective's real finding.

### Entity-by-entity evaluation

**`ChargingSession`** — generates revenue, and only this. It is the metered fact pattern a price must be applied to: `energyWh` (always resolvable without `MeterValue` rows, per CAP-004 §7/DEC-016), `startedAt`, `endedAt`, `meterStart`/`meterStop`. It is not a party — it doesn't owe money and doesn't receive money. It is the _event_ billing is computed from, structurally identical in role to a line-item's source data, not the line item's payer or payee.

**`AuthorizationCredential`** — identifies _how_ a session was authorized (RFID, app, etc.), and by FK, _which organization issued that credential_ (`AuthorizationCredential.organizationId`, `@@unique([organizationId, externalIdentifier])` — verified in schema). It does **not** identify an individual customer. Today, a credential's owner is the operating organization itself, not a person or fleet distinct from that organization. This means `AuthorizationCredential` cannot yet answer "who receives the charges" without conflating the operator with the customer — it answers "which method was used to start this session," a necessary but not sufficient fact for billing.

**`Organization`** — owns the invoice, in the same sense it already owns every other business record in this schema. Every `ChargingSession` carries `organizationId` directly (CAP-004's deliberate denormalization, DEC-013 precedent); a future `Invoice` would follow the identical pattern, for the identical reason (session-level query volume, tenant-scoped listing, and — per DEC-022 — the hard multi-tenant isolation boundary every business record in this system respects). Whether `Organization` is also the _payee_ (it bills its own end-users directly) or is itself somehow a _payer_ (e.g., a roaming session where a visiting network's organization owes the site-operating organization — DEC-018 already names roaming as a real future case) is a business-relationship question the schema does not yet model at all; there is no B2B invoicing concept between two `Organization` rows today.

**`Vehicle`** — **no Prisma model exists.** Named only as an "architectural concept" in CAP-004 §4 and MOVOS_CHARGING_SESSION_ARCHITECTURE's "Driver, fleet, and vehicle relationships" section — confirmed by schema inspection, not merely by citing those docs. If built, a `Vehicle` is a plausible target for internal cost _allocation_ (a fleet operator wants to know what vehicle #12 cost this month) but is not a realistic invoice recipient in a legal/payment sense — a vehicle does not hold a payment method; whoever owns or operates it does.

**`Driver`** — **no Prisma model exists**, same as `Vehicle`. This is the natural candidate for "who owes the money" in the ordinary public-charging (B2C) case — a person plugged in a car and should be billed for it. Its absence is not a narrow gap: **MOVOS currently has no representation of a paying customer at all.** `User` exists, but it is scoped to `Membership` — organizational staff/operator access, not a customer relationship. An operator cannot, today, express "this specific person owes $4.50" as a persisted fact anywhere in this schema. This is the central structural gap Objective 1 surfaces.

**`Connector`** — none of the three roles. It is a hardware/protocol attachment point (`type`, `maxPowerKw`, `status`), referenced by `ChargingSession.connectorId` for _context_ (which physical connector was used — relevant to tariff _selection_, e.g. a DC-fast tier priced differently than AC, per Objective 6's scenarios), never as a party to the transaction. It generates nothing, receives nothing, owns nothing.

### Summary

| Entity                    | Generates revenue                  | Receives charges (is billed)                                                    | Owns the invoice                                              |
| ------------------------- | ---------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `ChargingSession`         | **Yes** — the metered event itself | No                                                                              | No                                                            |
| `AuthorizationCredential` | No                                 | No — identifies the _method_, owned by the operator, not a customer             | No                                                            |
| `Organization`            | No                                 | Ambiguous — payee in the ordinary case; the B2B/roaming payer case is unmodeled | **Yes** — same tenant-ownership pattern as every other record |
| `Vehicle`                 | No                                 | No (not implemented; would be an allocation target at most, not a payer)        | No                                                            |
| `Driver`                  | No                                 | **Intended, eventually — not implemented today**                                | No                                                            |
| `Connector`               | No                                 | No                                                                              | No                                                            |

**Headline finding:** the entity that generates revenue (`ChargingSession`) and the entity that should owe the resulting debt (a customer — `Driver`, or a `Fleet`/counterparty `Organization` in a B2B case) are structurally different concepts, and MOVOS has a real, populated schema representation of only the first. Any billing implementation that follows this work order must either (a) accept that, in the near term, the debtor is an unmodeled/external concept (e.g., billed out-of-band, or represented only by whatever `AuthorizationCredential.metadata` an operator chooses to stuff in informally) or (b) treat introducing a real customer-representing entity as a prerequisite, not a follow-on. This document does not resolve which — see Objective 6's per-scenario walkthrough, where this gap has materially different consequences depending on the deployment shape.

## Objective 2 — Tariff semantics

**No recommendation is made in this section, per the work order.** Objective 7's decision document is where MOVOS actually chooses. This section evaluates the three named options against the three named questions only.

### Option A — Price fixed at session start

The applicable rate is read exactly once, at the moment the session begins (`StartTransaction`/`TransactionEvent(Started)`, the same instant `ChargingSession.startedAt` is set), and applies uniformly to every watt-hour the session ever delivers, however long it runs.

- **Mid-session price change:** has no effect. A tariff edit made by an operator five minutes into a two-hour session changes nothing about that session's bill — the rate captured at minute zero governs the whole thing.
- **After midnight:** if the tariff schedule differentiates day/night rates, a session starting at 23:58 and ending at 00:15 is billed **entirely** at the 23:58 (day) rate. Simple and maximally predictable to the person paying ("the price you saw when you plugged in is the price you pay"), but does not track the operator's own posted day/night rate structure for the portion of the session that actually happened at night.
- **During peak pricing:** identically — a session starting just before a peak window and running through it is billed entirely at the pre-peak rate, understating (or overstating, if peak is cheaper, which is unusual but not impossible) the operator's intended revenue for the peak-hours portion.

### Option B — Price recalculated continuously

The rate applied to each unit of energy is whatever the _live_ tariff says at the moment that energy was actually delivered — in effect, pricing at metering-interval granularity.

- **Mid-session price change:** takes effect immediately, splitting the session into rate-differentiated segments at the moment of change.
- **After midnight:** the day-rate energy and night-rate energy are billed separately and correctly, exactly reflecting when each watt-hour was actually delivered.
- **During peak pricing:** captures exactly the energy delivered during the peak window at the peak rate — the most revenue-accurate of the three options, by construction.
- **The real constraint this option runs into:** attributing energy to a specific moment in time, at sub-session granularity, requires time-series data — `MeterValue` rows. CAP-004/DEC-016 are explicit that `MeterValue` is **optional, sparse telemetry**: "the session lifecycle must never depend on telemetry availability," and some vendor devices send zero `MeterValues` messages for an entire session. Option B, taken literally, has no fallback for that case — there would be no data points to split the energy against, only the single start/stop totals `ChargingSession` always guarantees. Continuous recalculation is not just an accuracy improvement over Option A; it introduces a data-availability dependency the rest of this schema was deliberately built to avoid.

### Option C — Hybrid snapshot

A pricing-terms snapshot is captured whenever a pricing-relevant condition changes during a session — at minimum: session start; any admin-triggered tariff edit affecting the session's organization/site; entry into or exit from a scheduled peak window; a day/night schedule boundary (including midnight, when the tariff differentiates by time of day). Each snapshot bounds a time range within the session; the session's total is the sum, across snapshots, of (that snapshot's rate × energy delivered during its range).

- **Mid-session price change:** a new snapshot is written at the moment of change. Energy before the change is priced by the prior snapshot; energy after, by the new one. This is exactly DEC-018's original `TariffSnapshot` proposal, now with a concrete triggering rule instead of an open question.
- **After midnight / during peak:** the same mechanism — a snapshot boundary is inserted at the schedule transition, whether or not the underlying _tariff row_ changed value, because a scheduled day→night rate change is itself a pricing-relevant event even if no admin touched anything.
- **What Option C does not remove:** the same energy-attribution problem Option B has. Naming and bounding "these terms applied starting at this instant" does not, by itself, solve how to split a session's single `energyWh` total between two snapshot boundaries when there are few or zero `MeterValue` samples in between. That requires an explicit, separately-decided estimation rule (e.g., linear time-proportional allocation of total energy across the elapsed time in each snapshot's range, when direct meter data is unavailable) — a real, unresolved implementation detail this document surfaces rather than glosses over. Option C is a strictly better _container_ for handling mid-session price changes than A or B alone; it does not, on its own, guarantee accurate sub-session energy attribution when telemetry is sparse.

### What none of the three options change

All three are compatible with CAP-004/MOVOS_CHARGING_SESSION_ARCHITECTURE's standing constraint that `ChargingSession` grows no pricing fields of its own. Whatever the eventual entity shape, it sits beside `ChargingSession`, referencing it, never inside it.

## Objective 3 — Billing ownership

### The chain as posed

```
Organization
    ↓
Site
    ↓
ChargingSession
    ↓
TariffSnapshot
    ↓
Future Invoice
```

This matches the schema's actual ownership pattern exactly through `ChargingSession` (`Organization.chargingSessions`, `Site.chargingSessions` — both denormalized directly per CAP-004 §2, verified in schema) and is architecturally consistent for the two links that don't exist yet (`TariffSnapshot`, `Invoice`) with DEC-018's already-published recommendation.

### Who owes the money?

Unresolved by the current schema — this is the same gap Objective 1 found, restated in ownership terms. The debt is conceptually owed by whoever authorized/consumed the session, but the only existing schema path from a session to "who used it" is `ChargingSession.authorizationCredentialId → AuthorizationCredential`, and `AuthorizationCredential` belongs to the _operating_ organization, not a customer. For a deployment where the operator bills its own accountless walk-up customers (a plausible shape for several of Objective 6's scenarios), the debtor may not correspond to any persisted entity at all — the debt is owed by "whoever was physically present," a fact the system has no durable way to name today. Introducing a real payer-representing entity (`Driver`, a B2B counterparty `Organization`, or something else) is a precondition for answering this question for real, not a detail this document can resolve by picking among existing tables.

### Who receives the money?

The operating **`Organization`** — the tenant that owns the `Site`/`ChargingStation`/`ChargingSession` chain the energy was delivered through. This is symmetric with Objective 1's "owns the invoice" finding: in the ordinary case, the entity that owns the invoice and the entity that is owed the money are the same `Organization`. The exception is the B2B/roaming case DEC-018 names (a visiting network's organization owes the site-operator's organization) — genuinely different from the ordinary case, and not modeled by anything in this schema today.

### What survives organization deletion?

**Verified against the shipped schema, not assumed:** no `onDelete` behavior is specified anywhere in `prisma/schema.prisma` — every foreign key relation therefore uses the implicit Postgres/Prisma default, which rejects the delete outright if any dependent row exists (`ON DELETE NO ACTION`, equivalent in practice to `RESTRICT` for this purpose). Concretely, **an `Organization` with any existing `Site`, `ChargingSession`, `AuthorizationCredential`, `Membership`, or `AuditEvent` row cannot be hard-deleted today at all** — the database rejects the operation with a foreign-key constraint violation before any row is touched.

The only deletion-adjacent operation that actually exists and is exercised in shipped code is a **status transition**, not a row deletion: `OrgStatus`/`SiteStatus` both include `ARCHIVED`, and `sites.service.ts` implements a real `archive()` method that flips `Site.status` — confirmed in code, not inferred from the enum's existence alone. Archival changes nothing about referential integrity; every row underneath an archived `Organization` remains exactly as queryable and exactly as intact as before.

**This happens to already be the correct answer for billing/financial retention** — nothing billing-relevant can be lost to a cascading delete, because no cascade exists anywhere in this schema. It is worth stating plainly, though, that this is an **emergent property of conservative FK defaults, not a deliberate financial-record-retention policy anyone designed.** Whoever eventually adds `Invoice`, `Payment`, or `TariffSnapshot` models should be aware that the safety observed here is inherited "for free" only as long as those new models' relations are _also_ left without an explicit `onDelete: Cascade` — adding one to any FK on the path from `Organization` down to a future `Invoice` would silently reintroduce a financial-data-loss vector that does not exist in the schema today.
