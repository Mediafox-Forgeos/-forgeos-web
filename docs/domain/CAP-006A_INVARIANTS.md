## Objective 1 — the locking-strategy evaluation

The work order required evaluating all four options before choosing, not assuming an implementation. Evaluated against: does it actually prevent the race (§1's connector-level race in the audit), what does it cost in complexity/contention, and does it degrade gracefully for the _legitimate_ concurrent case (a genuine StartTransaction retransmission, which must still return the existing session, not error out)?

| Option                                         | Prevents the race?                                                                                                                                                                                                                                                                                                                                                             | Cost / complexity                                                                                                                                                                    | Graceful degradation?                                                                                                                                                                                                                                                                      | Verdict                                                                                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **`SELECT ... FOR UPDATE`**                    | Only if there's an existing row to lock — but the race is precisely about _whether a row exists yet_; there's nothing to `FOR UPDATE` before the first insert. Locking the parent `Connector` row instead works, but over-broadens the lock to contend with every unrelated `Connector` read/write in the app (status updates, EVSE listing, etc.), not just session creation. | Medium — needs a real row and a transaction, and the "what do we lock" question doesn't have a clean answer for the create case.                                                     | Poor — a losing transaction blocks until the winner commits, then still has to re-check and branch itself; no free "return existing" behavior.                                                                                                                                             | Rejected — no natural lock target for the create path.                                                                                        |
| **Advisory lock (`pg_advisory_xact_lock`)**    | Yes — an application-defined lock keyed on an arbitrary identifier (`connectorId`), scoped to the transaction, released automatically at commit/rollback. Requires no target row to exist.                                                                                                                                                                                     | Low — no schema change for the lock itself, no risk of colliding with unrelated row-level locks elsewhere in the app.                                                                | Good — the losing call blocks, then re-reads _inside_ the same transaction and can branch cleanly (return existing / reject with a reason), which is exactly the idempotent-return semantics `createSession` already promised.                                                             | **Chosen.**                                                                                                                                   |
| **Optimistic concurrency (retry-on-conflict)** | Only with a real constraint to detect the conflict at write time (see the partial unique index below) — optimistic concurrency alone (a version column, compare-and-swap) doesn't stop two concurrent _creates_, since there's no existing row to compare a version against.                                                                                                   | Medium — needs retry logic at every call site, and retries change response latency unpredictably under contention.                                                                   | Poor for this specific case — a hard constraint violation is a blunt instrument; turning "loser gets an existing-row response" into a clean outcome requires bolting the same catch-and-requery logic onto every retry, at which point most of the benefit of "no locking" is gone anyway. | Rejected as the _primary_ mechanism — but its underlying idea (a DB-level constraint as a safety net) is kept as defense-in-depth, see below. |
| **Connector reservation table**                | Yes, in principle — a dedicated `ConnectorReservation` row per connector, locked/updated as a semaphore.                                                                                                                                                                                                                                                                       | High — a new table, a new migration, a new entity to keep in sync with `Connector`'s own lifecycle (creation, deletion), for a guarantee an advisory lock already provides natively. | Same as advisory lock, once built.                                                                                                                                                                                                                                                         | Rejected — reinvents what Postgres already offers, at real ongoing maintenance cost, for zero additional guarantee.                           |

**Chosen: advisory transaction lock as the primary mechanism, backed by a partial unique index as defense-in-depth.** Even with correct locking discipline today, a future code path could forget to acquire the lock (a new handler, a script, a migration backfill). The partial unique index makes Invariant 1 true _at the database level_, independent of any application code's discipline — consistent with this project's existing precedent of backing business rules with real constraints (DEC-016's non-negative-energy `CHECK`s), not just service-layer checks.

**A documented tradeoff, not hidden:** the advisory lock key is `hashtext(connectorId)::bigint` — a 32-bit hash of the connector's cuid. Two different connectors could theoretically hash to the same key (a collision), causing them to serialize against each other unnecessarily. This is a performance cost (slightly less concurrency than theoretically possible), never a correctness cost (extra serialization is always safe) — not fixed here since it isn't a real risk at MVP scale; a 64-bit hash (`hashtextextended`) would reduce it further if ever measured as a bottleneck.

## Invariant 1 — At most one non-terminal `ChargingSession` per connector

**Enforced by two independent layers**, per the evaluation above:

1. **Database:** partial unique index `ChargingSession_connectorId_nonterminal_key` on `(connectorId) WHERE status IN (PENDING, AUTHORIZED, STARTING, ACTIVE, SUSPENDED, OFFLINE, STOPPING)` — migration `20260802055353_add_connector_nonterminal_unique_index`. This is true regardless of any application code's correctness.
2. **Application:** `SessionLifecycleService.createSession` and `SessionLifecycleService.recoverOfflineSession` both wrap their existence/conflict check and their write in one `$transaction`, holding `pg_advisory_xact_lock(hashtext(connectorId)::bigint)` for the duration — the same lock key for both methods, so a concurrent create and a concurrent recovery on the _same connector_ cannot interleave (this is what closes the exact race PR27_ARCHITECTURAL_AUDIT.md §1 demonstrated). `createSession` additionally catches a unique-index violation (Postgres code `P2002`) as a graceful fallback to "return the existing row" — the same response a legitimate retransmission already produces, so the defense-in-depth layer degrades exactly as gracefully as the primary one.

**Proof, not just assertion:** `session-lifecycle.service.spec.ts`'s `createSession` tests, `connectivity-coordinator.service.spec.ts`'s recovery tests, and the CAP-006A concurrency tests described in §"Testing" below (real, not mocked, concurrent calls against a real Postgres instance).

## Invariant 2 — Recovery never creates sessions

`SessionLifecycleService.recoverOfflineSession` contains exactly one write path: `tx.chargingSession.update(...)`. There is no `create` call anywhere in this method, and it operates on a `sessionId` the caller already resolved from an existing `OFFLINE` row — it cannot conjure a new one into existence. `ConnectivityCoordinator.attemptRecovery` calls this method and this method alone for the recovery path; it never calls `SessionLifecycleService.createSession`. Verified directly by reading both methods, not merely asserted — `createSession` and `recoverOfflineSession` are the only two entry points into this service that can change a session's identity or bring a row into existence at all, and they are distinct, non-overlapping code paths.

## Invariant 3 — Reconnect is idempotent

`recoverOfflineSession` re-reads the session's status _after_ acquiring the connector's advisory lock, not before. If a concurrent call (a duplicate reconnect event, or a `StopTransaction` that landed first) already resolved the session, this fresh read sees a non-`OFFLINE` status and returns `{ outcome: 'already-resolved' }` — a clean no-op, not a re-application of the recovery logic and not an error. `ConnectivityCoordinator` records no audit event for this outcome, since the event that actually resolved the session already owns that trail (recording a second event here would itself be a form of non-idempotence — a duplicate audit record for one real occurrence). Proven by `connectivity-coordinator.service.spec.ts`'s "records no audit event when recovery finds the session already resolved" test and the runtime validation's duplicate-reconnect scenario (see CAP-006A_VALIDATION.md).

## Invariant 4 — No orphan `ACTIVE` sessions

**True with a bounded latency, not an instantaneous guarantee — stated precisely, not oversold.** `OrphanSessionSweepService` (new in CAP-006A) closes the gap CAP-005 left open: a session whose station cleanly disconnected and never reconnected had no automatic path forward at all. The sweep finds any non-terminal session (`ACTIVE`, `SUSPENDED`, `OFFLINE`) whose station has lacked connectivity evidence — `COALESCE(lastDisconnectedAt, lastConnectedAt, session.startedAt)` — for longer than `ConnectivityCoordinator.RECOVERY_WINDOW_MS` (15 minutes, the same window recovery itself uses, deliberately not a second independently-tunable threshold), and expires it to `FAILED`/`NETWORK_FAILURE`.

Why reuse `FAILED`/`NETWORK_FAILURE` rather than a new `EXPIRED` status (which the work order offered as one option among several — "or another lifecycle"): `ACTIVE|SUSPENDED|OFFLINE → FAILED` is already a valid, already-tested transition in `ALLOWED_TRANSITIONS`, and `NETWORK_FAILURE` is already a real `ChargingSessionTerminationReason` value whose meaning ("the session ended because connectivity was lost, not because it completed normally") is exactly the semantic this backstop needs. Adding a new status value would require a migration, would need every existing status-set consumer (queries, transition-table entries, frontend badges) to decide whether to treat it as terminal, and would buy nothing a reused value doesn't already provide. This is judged the better call, not a shortcut.

**The honest bound:** the sweep runs every 60 seconds and only considers sessions past the 15-minute window, so the realistic worst case is "no session survives orphaned for longer than ~16 minutes," not "zero latency." This is the same class of bound the recovery window itself already accepts — a session isn't abandoned as unrecoverable before ARGOS's own approved 15-minute policy says it's fair to. No session is a _permanent_ orphan; some are orphaned for up to ~16 minutes before this backstop fires, matching the same window a station's own device would have to reconnect within anyway.

**Does not double-fire with the recovery path or the stale-close path:** a session already `OFFLINE` and _within_ its recovery window is not touched by the sweep (`COALESCE(...) < threshold` excludes it); a session that successfully recovers before the threshold reverts to `ACTIVE` under an `ONLINE` station, which the sweep's `connectivityStatus != 'ONLINE'` clause also excludes.

## Invariant 5 — Connectivity events never corrupt billing data

**No connectivity-triggered code path (CAP-005's stale-close, CAP-006A's recovery, or CAP-006A's orphan expiry) ever writes `meterStart`, `meterStop`, or overwrites `energyWh`.** `suspendSession`/`resumeSession`/`recoverOfflineSession` change only `status`. `failSession` (the orphan sweep's terminal call) sets `status`, `terminationReason`, and `endedAt` — it does **not** set `meterStop` or finalize `energyWh` the way `stopSession` does. This is a deliberate, narrow claim: connectivity events never _corrupt_ an existing value (nothing here ever overwrites `meterStart`/`meterStop`/`energyWh` with wrong data), but an orphan-expired session's `energyWh` is left at whatever it last was when connectivity was lost, not finalized as `meterStop - meterStart` the way a normal `stopSession` completion is — because there is no final device-reported `meterStop` for a session that never sent a `StopTransaction`. **This is a real, open question this invariant does not resolve**, not a corruption: what a billing system should do with a `FAILED`/`NETWORK_FAILURE` session's necessarily-incomplete energy figure is exactly the kind of question [DEC-018's billing boundary analysis](./DEC-018_BILLING_BOUNDARY_ANALYSIS.md) exists to eventually answer, and DEC-018 remains unimplemented. CAP-006A's contribution to Invariant 5 is narrower and fully honest: it guarantees connectivity handling never silently corrupts a billing-relevant field — it does not guarantee every connectivity-driven termination produces billing-complete data, because no code path can invent a `meterStop` value the device never reported.
