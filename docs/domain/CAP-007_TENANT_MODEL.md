# CAP-007 — Tenant & Organization Foundation

**Generated:** 2026-08-02 (WO-ARGOS-013)
**Answers:** "Who owns what?"
**Scope:** no new business capability. No billing, RFID, smart charging, or OCPP 2.0.1.

---

## 0. A finding this document is built on, not around

WO-ARGOS-013 proposed introducing a new `Tenant` entity (with `Site`/`Membership` beneath it) to represent "an independent company or customer." Before writing any schema, this was checked against the shipped codebase: **`Organization` already is that entity.**

| WO-ARGOS-013's proposed `Tenant`                                                                      | Already exists as                                                                                                                                               |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Tenant { id, legalName, displayName, slug, taxId, country, timezone, status, createdAt, updatedAt }` | `Organization { id, name, slug, status, createdAt, updatedAt }` — missing only `legalName`, `taxId`, `country`, `timezone`                                      |
| `Site { id, tenantId, name, address, city, country, latitude, longitude }`                            | `Site { id, organizationId, name, address, city, latitude, longitude, ... }` — already richer (10 additional location fields from the location-enrichment work) |
| `Membership { id, userId, tenantId, role }`                                                           | `Membership { id, userId, organizationId, role, status }` — exists verbatim, including the field the proposal omitted (`status`, for invite/suspend lifecycle)  |
| `Tenant → Site → ChargingStation → EVSE → Connector`                                                  | `Organization → Site → ChargingStation → Evse → Connector` — the exact hierarchy CAP-002 through CAP-006A are already built on                                  |
| Role evaluation (`SUPER_ADMIN`, `TENANT_ADMIN`, `OPERATOR`, `SUPPORT`, `VIEWER`, `FLEET_MANAGER`)     | `MemberRole { OWNER, ADMIN, OPERATOR, SUPPORT, ANALYST, VIEWER }` already covers 4 of 6 by direct correspondence                                                |

**ARGOS confirmed the resolution before implementation began** (a genuinely blocking ambiguity — see the "why this matters" note below): treat this work order's "Tenant" as the existing `Organization`, extended in place. No rename. Every deliverable below is framed against `Organization` as it already exists, not against a new parallel entity.

**Why this matters, concretely:** the codebase already uses the word "tenant" for something else entirely — `apps/movos-web/src/config/tenant.ts` is the white-label _product branding_ configuration object (which reseller's name/colors/currency skin the app wears), unrelated to customer data isolation. Introducing a data-model entity literally named `Tenant` would have created two different meanings of "tenant" in the same codebase — a real, avoidable source of confusion this decision sidesteps entirely.

**What this means for scope:** CAP-007 is not a from-scratch build. It is (1) a small, additive schema extension (four new nullable columns, one new role value), (2) a rigorous audit of whether the _isolation_ the existing model promises is actually enforced everywhere, (3) closing any real gaps that audit finds, and (4) documenting all of it precisely. Sections below are ordered to make that distinction clear — "already true" vs "added by this work order" vs "evaluated, not implemented."

## 1. Ownership — who owns what (today, verified against the schema)

```
Organization
    ↓ (organizationId, required, RESTRICT)
Site
    ↓ (siteId, required, RESTRICT)
ChargingStation
    ↓ (chargingStationId, required, RESTRICT)
Evse
    ↓ (evseId, required, RESTRICT)
Connector
```

- **ChargingStation, Evse, Connector**: own no `organizationId` column directly — ownership is derived by walking the parent chain. This is the established CAP-002 pattern, unchanged here.
- **ChargingSession, AuthorizationCredential, AuthorizationAttempt**: denormalize `organizationId` directly onto the row (CAP-004's documented, deliberate exception — session-level query volume doesn't tolerate a 4-way join). `ChargingSession` additionally denormalizes `siteId`, `chargingStationId`, `evseId`, `connectorId`.
- **Tariffs, Invoices, Fleets**: **do not exist as models.** No schema, no code, no artifact of any kind — confirmed by the same grep-based verification every prior Atlas/Feature-Matrix update in this project has used. This document does not invent them to answer the WO's ownership question prematurely; seeCAP-007_ISOLATION_INVARIANTS.md Invariant 4 for how the _future_ Invoice model should inherit ownership, stated as a design constraint on that future work, not as code shipped now.
- **Users**: belong to zero or more Organizations via `Membership` (already many-to-many, already exists).

### 3.1 `FLEET_MANAGER` — schema addition

Added to the `MemberRole` enum. No guard currently checks for it (nothing to check — no fleet endpoints exist). This is intentionally the full extent of this addition: a vocabulary slot reserved for CAP-integration with a future Fleet capability, not a functioning permission today. Flagging this precisely so it is never mistaken for "fleet permissions are implemented."

### 3.2 `SUPER_ADMIN` — why it cannot be a `MemberRole` value, and what it should be instead

`Membership.role` is scoped to exactly one `organizationId` per row (`@@unique([userId, organizationId])`) — a `Membership` _is_ "this user's role within this one organization." `SUPER_ADMIN`'s entire defining property — "sees everything, across every organization" — is not a stronger version of an organization-scoped role; it is a different _kind_ of authority that doesn't have an organization to be scoped to. Modeling it as a `MemberRole` value would require either (a) a platform-staff user holding a `Membership` row in _every_ organization (operationally absurd — a new row required for every future customer, forever), or (b) `OrgContextGuard` special-casing a role value to bypass the very membership check it exists to enforce (a security-relevant special case buried inside the tenant-isolation guard itself — exactly the kind of thing that causes isolation bugs).

**Recommended (not implemented in this work order):** a `User.platformRole` field (e.g. `PlatformRole { NONE, SUPER_ADMIN }`, default `NONE`), checked by a _separate_, explicit guard (`PlatformAdminGuard`) applied only to genuinely global routes — never folded into `OrgContextGuard`. This keeps the tenant-isolation guard's logic simple and auditable (it only ever answers "is this user a member of this org"), and keeps platform-staff access an explicit, separate, and rare code path. **Not implemented here** because zero routes currently need it (no `/admin/*` surface exists yet — see §2's `Issue invoices`/audit-log note) and adding an unused authority mechanism ahead of any consumer is exactly the kind of speculative building this engagement's discipline avoids. Recorded here as an evaluated, justified design so the future work that needs it (the first real `/admin/*` endpoint) doesn't have to re-derive this reasoning.

## 4. Ownership inheritance rules (stated explicitly, per the WO's request)

- **Sessions never exist outside a tenant.** `ChargingSession.organizationId` is a required (non-nullable) column with an `ON DELETE RESTRICT` foreign key — the database itself refuses both a session with no organization and the deletion of an organization that still has sessions.
- **Connectors cannot change tenant.** No API surface accepts a `Connector` (or `Evse`, or `ChargingStation`) transfer between parents — confirmed by reading `CreateChargingStationDto`/`UpdateChargingStationDto` (no `siteId` field in either; `siteId` is fixed by the route, `PATCH /charging-stations/:id` cannot move a station to a different site, let alone a different organization). This is the current, correct state — not a gap.
- **Station transfer requires migration.** Consistent with the above: today, moving a `ChargingStation` (and everything beneath it) to a different `Site`/`Organization` has no API path at all — the only way to do it is a direct, audited, out-of-band database operation. This is deliberate. Building a self-service "transfer this station" endpoint is real feature work with its own authorization/audit/billing-implication questions, explicitly out of this work order's scope.

## 5. Migration strategy — how existing records receive a tenant

**The premise of this question doesn't apply the way it was posed, and that's worth stating plainly rather than answering around it.** "How do existing records receive a tenant?" presumes records currently exist _without_ tenant ownership that need retrofitting (the classic multi-tenancy-bolted-on-later migration problem). That is not this codebase's situation: every `Site`, `ChargingStation`, `ChargingSession`, `AuthorizationCredential`, and `AuthorizationAttempt` row has always had an `organizationId` (or a derivable one through its parent chain) from the moment CAP-002 introduced the model — because the isolation model was designed in from the start, not added after the fact.

What CAP-007 actually adds to `Organization` are four new **nullable** columns (`legalName`, `taxId`, `country`, `timezone`) — nullable specifically so the migration requires no backfill decision and no default-tenant/bootstrap-tenant scaffolding: existing rows (today, just "Kylum Energy") simply have `NULL` in the new fields until someone fills them in, exactly like any other optional-field addition. **Chosen: no migration script, no default tenant, no bootstrap tenant — because none is needed.** The three options the WO asked to evaluate (default tenant / migration script / bootstrap tenant) all solve a problem — "some rows have no tenant" — that does not exist here, and manufacturing one of them anyway would be solving a problem this codebase doesn't have.

## 6. Database requirements

See [CAP-007_ISOLATION_INVARIANTS.md](./CAP-007_ISOLATION_INVARIANTS.md) for the FK/cascade audit (every relation's `ON DELETE` behavior, justified) and [CAP-007_API_TENANT_MATRIX.md](../reviews/CAP-007_API_TENANT_MATRIX.md) for the endpoint-by-endpoint scoping audit.

**Schema-only for this pass.** The four new `Organization` fields (`legalName`, `taxId`, `country`, `timezone`) are not yet exposed through `toApiOrganization`/`ApiOrganization`, and no endpoint exists to write them (`GET /organizations` remains the only `Organization`-returning route, and it returns nothing new). Wiring them into the API is real, scoped feature work of its own (an update endpoint needs its own authorization rule — presumably `OWNER`-only — and validation per field, e.g. IANA timezone/ISO country-code checks) deliberately left for whichever future capability first needs to read or write them, rather than built ahead of any consumer.

## 7. Explicitly out of scope

Billing, tariffs, invoices, fleets, RFID-specific behavior, smart charging, OCPP 2.0.1, a `/admin/*` platform-staff surface (the `PlatformAdminGuard` design in §3.2 is evaluated, not built), and any station-transfer API (§4). These exclusions are implementation limits, not architectural omissions — each has a stated ownership/inheritance answer above for when it does get built.
